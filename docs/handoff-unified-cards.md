## 2. Новое продуктовое решение — обязательно

Владелец не хочет отдельные карточки голов. Итоговая карточка материнского объекта содержит выбор представления: Дракон Края — сущность/голова; Пиглин, зомби, крипер, соответствующие скелеты — сущность/голова или череп. Медный голем — сущность/статуя, у статуи standing/sitting/running/star. Степени окисления и waxed маршруты не терять; объединение сущности со статуей не является разрешением слить все стадии окисления без отдельного решения.

Сохранять исходные block IDs, исходные записи/resources и возможность открытия старого объекта/PNG. Открытие piglin_head должно привести в материнскую карточку с выбранной головой. Это presentation family, а не заявление об эквивалентности объектов через обычный duplicate alias. Конкретные названия/структура cross-kind ключей ещё не реализованы.

Один общий лист использовать напрямую. Переключение сущность/голова меняет геометрию и используемые UV, не обрезает PNG и не создаёт отдельную копию развёртки. Если у форм реально разные файлы, сохранить оба набора ресурсов: объединение карточки не значит выдумывать общий файл.

Выбор редактируемой текстуры должен быть независим от выбора модели/формы и её параметров. Открытие PNG не должно самовольно переключать уже выбранную форму. Использовать общий подход меню состояний поршня, без отдельной панели для каждого семейства. Видимые подписи EN/RU, ID не переводить, сохранить paper/design tokens.

Пока полная сущность не перенесена, не выдавать её за доступную модель. Предложенный подход — подготовить общую карточку с реально доступной формой и добавлять полную entity-форму по готовности. Это предложение реализации, не уже записанный контракт.

Сначала определить и переработать общий контракт и его потребителей. Конкретная новая схема ещё не утверждена кодом.

## 5. Как работать — прямое требование владельца

Найти, где ответственность уже реализована; прочитать связанные вызовы; переписать/отредактировать существующий участок и его потребителей, при необходимости существенно. Без костылей, цепочек monkey-patch, адаптеров вокруг адаптеров, второго каталога и дополнительных специальных меню. Отдельный модуль геометрии допустим и не равен отдельной видимой карточке. Не переписывать несвязанный рабочий код ради объёма diff.

Владелец не торопит: полный рефакторинг идёт маленькими самосогласованными пакетами. Точечная проверка изменяемого поведения уместна; общий аудит, техчистка и расширение CI не заменяют перенос. Каждая запись требует полного точного подтверждения, затем проверки сохранённого diff; после сверки самостоятельно начать следующий шаг. Не перекладывать техническую отладку на владельца.

Предложенная очередь: проверить текущий HEAD/непопавший states пакет; переработать общую селекцию карточка→представление→source/model; подключить общий UI по подходу меню поршня; глазоцвет как первый законченный пример; применить к головам и голему с настоящими источниками/entities. Пиглин как первый cross-kind пример обсуждался, но полный entity adapter пока отсутствует. Порядок допустимо уточнить по реальной связности кода.
